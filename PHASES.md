# MergeMaster AI: Architecture and Implementation Phases

## 🏗️ Architecture Plan

The application follows a modern decoupled architecture emphasizing real-time updates, AI-driven backend orchestration, and a snappy frontend experience.

### 1. Frontend Layer (DevOps Command Center)

- **Framework:** TanStack Start (React) for optimized routing and SSR.
- **Styling:** Tailwind CSS + shadcn/ui to build a professional, dark-mode, enterprise-grade interface.
- **Real-time Database & State:** Convex for storing PR metadata, Risk Scores, and routing rules. Convex allows instant syncing to the frontend without manual polling.

### 2. Backend API Layer

- **Framework:** FastAPI (Python) for asynchronous handling of GitHub webhooks and non-blocking LLM task management.
- **Validation:** Pydantic v2 to enforce strict JSON schemas on AI outputs.
- **Integration:** PyGithub and GitHub Webhooks API to read PR diffs, post comments, and push remediation commits.

### 3. AI & Orchestration Layer

- **Agent Framework:** LangGraph (Python) to power the multi-agent pipeline workflow.
- **Primary Model:** IBM Granite, optimized for code reasoning and generating structured outputs.
- **Development Partner:** IBM Bob for boilerplate, nodes, and GitHub API logic generation.

### 4. Convex Database Schema (Real-time State)

To support the real-time DevOps Command Center and secure user access, the following core tables (documents) will be defined in the Convex schema:

- **`users`**: Engineering managers and developers logging into the dashboard (via GitHub OAuth).
  - `github_id` (String) - The OAuth provider's user ID.
  - `name` (String) - Display name.
  - `email` (String) - Contact email.
  - `role` (String) - e.g., "admin", "manager", "engineer" for role-based access to override decisions.

- **`pull_requests`**: Tracks the active PRs and their current AI-evaluated state.
  - `github_pr_id` (String or Number) - The ID from GitHub.
  - `repo_name` (String) - Target repository.
  - `title` (String) - PR title.
  - `author` (String) - PR author's GitHub handle.
  - `status` (String) - e.g., "pending", "approved", "blocked".
  - `risk_score` (Number) - 0 to 100 confidence score generated by the Analyst Node.
  - `ai_summary` (String) - High-level AI summary of the PR.
  - `updated_at` (Number) - Timestamp for real-time frontend syncing.

- **`routing_rules`**: Defines how the Orchestrator Agent assigns reviewers.
  - `file_pattern` (String) - e.g., `schema.prisma`, `*.css`, `*.md`.
  - `reviewer_role` (String) - e.g., "Lead Backend Engineer", "UI/UX Lead".
  - `auto_approve` (Boolean) - Whether changes to this pattern can be auto-approved (e.g., minor docs).

- **`ai_decisions_log`**: Audit trail for actions taken by MergeMaster.
  - `pr_id` (Id("pull_requests")) - Reference to the PR.
  - `decision_type` (String) - e.g., "block_merge", "route_reviewer", "remediate_code".
  - `reasoning` (String) - The LLM's justification for the action.
  - `overridden_by` (Id("users"), Optional) - Reference to the manager who overrode the decision via the dashboard.
  - `created_at` (Number) - Timestamp.

## 📅 Implementation Phases

The features have been broken down into progressive phases to ensure a smooth, logical build from foundation to advanced autonomous agents.

### Phase 1: Foundation & The DevOps Command Center ✅ Implemented

_Focus: Setting up the core infrastructure and frontend interface._

- Initialize the TanStack Start frontend repository.
- Configure Tailwind CSS and shadcn/ui.
- Set up Convex database schemas for PR metadata, routing rules, and AI risk scores.
- Build the core dashboard UI:
  - Active PRs list.
  - Real-time Risk Score visualization.
  - Controls to view AI decisions and override them.

### Phase 2: Backend Infrastructure & GitHub Hooks ✅ Implemented

_Focus: Establishing the connection between GitHub and the application._

- Set up the FastAPI backend environment (Python 3.10+).
- Define strict Pydantic v2 schemas for expected data.
- Implement endpoints to receive and parse GitHub Webhooks (e.g., PR opened/updated events).
- Integrate PyGithub to authenticate and fetch raw code diffs and file paths.

### Phase 3: AI Pipeline & Smart Reviewer Routing ✅ Implemented

_Focus: Introducing the AI reasoning and basic orchestration._

- Initialize the LangGraph framework in the backend.
- Integrate the IBM Granite model via API.
- **Diff Extraction Node:** Parse diffs securely for the AI.
- **Smart Reviewer Routing (Orchestrator Agent):**
  - Analyze touched files (e.g., `schema.prisma` -> Backend Lead, `globals.css` -> UI/UX Lead).
  - Implement auto-approval logic for minor markdown/docs typos.

### Phase 4: Release Decision Engine & Risk Scoring ✅ Implemented

_Focus: Evaluating code quality and enforcing deployment gates._

- **Analyst Node:** Prompt IBM Granite to evaluate extracted code for logic errors, bugs, and security risks.
- Generate the **Risk Confidence Score** (0-100%).
- Write scores and summaries to Convex to sync instantly with the Phase 1 dashboard.
- Enforce gatekeeping rules: if score >95%, clear the PR; if a critical flaw exists, block the GitHub merge state and log a Blocker ticket.

### Phase 5: Autonomous Code Remediation ✅ Implemented

_Focus: Reaching full autonomy for bug fixing._

- Build the **Committer Agent** within the LangGraph pipeline. ✅ `backend/committer_agent.py` — Granite `FixDraft` drafting with heuristic fallback (hardcoded JS/TS secrets → `process.env.*`; destructive SQL/dynamic exec → no safe fix).
- Implement logic where, upon finding a critical bug in Phase 4, the Committer Agent drafts a corrected code block. ✅ Graph: `route_reviewers -> [committer_agent if blocked] -> enforce_gate -> record_result`; success flips PR to `pending` and logs a `remediate_code` decision.
- Use PyGithub to autonomously push the fix as a new commit directly to the PR branch. ✅ `apply_fixes` pushes via `repo.update_file` on the PR head ref (exact unique snippet match required); the follow-up `synchronize` webhook re-runs the pipeline to re-verify.
